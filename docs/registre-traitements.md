# Registre des traitements de données personnelles

Les traitements de données personnelles de K-B : ce qui est écarté dès la collecte, ce qui est
gardé et combien de temps, et la procédure de tri qui tient ces durées. Une fiche par finalité,
comme le recommande la CNIL. Les tables citées sont celles de [stockage.md](stockage.md).

Une donnée publique reste une donnée personnelle : un nom d'auteur ou un login rattaché à une
personne entre dans le registre, même publié par la personne elle-même.

Contexte : K-B est un outil pour une seule utilisatrice, mené dans le cadre de sa formation.
L'exemption des activités strictement personnelles ou domestiques (RGPD art. 2.2.c) y est
**douteuse** : le considérant 18 l'exclut dès qu'il y a un lien avec une activité
professionnelle, et la Cour de justice de l'Union européenne interprète l'exemption strictement
(arrêt Ryneš, C-212/13, 11/12/2014). Le registre est tenu pour cette raison.

**Responsable des traitements** : l'utilisatrice de K-B, propriétaire du dépôt, dans le cadre de
sa formation, sur une ressource fournie par l'organisme.

**Sous-traitant** : Microsoft, pour l'appel du modèle qui rédige les fiches de veille (Azure AI
Foundry, zone de données UE), sur l'abonnement Azure de l'organisme de formation de
l'utilisatrice, fourni pour son projet de certification. Le client de Microsoft est l'organisme ;
Microsoft est son sous-traitant, selon le *Microsoft Products and Services Data Protection
Addendum* (DPA). Voir la section « Envoi des items au modèle des fiches ».

## Fiche 1 — Veille technologique

| Rubrique | Contenu |
|---|---|
| Finalité | Suivre l'actualité tech (papiers, vulnérabilités, versions, dépôts, articles) et répondre à « quoi de neuf cette semaine ». |
| Base légale | Intérêt légitime (art. 6.1.f) : veille professionnelle et formation. Les données sont publiées par les personnes elles-mêmes pour être diffusées, et réduites à un nom. |
| Personnes concernées | Auteurs de papiers arXiv, auteurs de releases et d'alertes GitHub, personnes créditées dans une alerte GitHub, personnes citées dans les notes d'une release, propriétaires d'un dépôt du top 100 GitHub, propriétaires d'un dépôt d'un classement GH Archive (dépôts qui montent). |
| Données | Noms des auteurs d'un papier, en liste JSON dans l'ordre d'arXiv (`publication.authors`). Login GitHub : brut seulement, sauf celui du propriétaire d'un dépôt d'un classement GH Archive, gardé dans le nom du dépôt (`trend.repository_name`), et sauf un login ou une @mention écrits dans les notes d'une release, gardées telles que reçues (`release.body`). Constat sur la collecte du 2026-10-07 : 12 des 100 notes de release contiennent un `@mot` (`@Claude`, `@file`, `@mention`, `@team`…) ; aucun n'a été vérifié comme étant un compte. Le brut GitHub contient aussi, pour chaque compte cité (auteur, personne créditée, propriétaire), son identifiant numérique et l'URL de son avatar, qui peut être une photo de la personne : brut seulement. |
| Destinataires | L'utilisatrice ; les agents qu'elle lance, par l'API REST. Sous-traitant : Microsoft (Azure AI Foundry, zone de données UE), sur l'abonnement de l'organisme de formation de l'utilisatrice, qui reçoit les champs envoyés des items pour rédiger les fiches de veille, puis, pour le LLM juge, les affirmations gardées et les champs des items qu'elles citent, sans les auteurs ; contrat : le DPA de Microsoft, entre Microsoft et l'organisme (section « Envoi des items au modèle des fiches »). Destinataires possibles chez l'organisme : voir la même section. Destinataire passé : Google, le 16/10/2026, repli terminé (section « Repli temporaire chez Google »). |
| Transferts hors UE | Quand un agent comme Claude Code lit les items par l'API, les noms d'auteurs lus partent chez le fournisseur du modèle, aux États-Unis. Cadre juridique de ce transfert non vérifié. |
| Durée de conservation | Celle du mode d'acquisition de la source, tenue dans `src/k_b/core/config.py` (`RETENTION_YEARS_BY_ACQUISITION_MODE`) : pour la veille (`watch`), **2 ans après la collecte**, dans la base et dans le brut (provisoire, à confirmer dans #20). Le brut et la base ont la même durée : la base doit rester reconstructible depuis le brut. Exception, CISA KEV (sans donnée personnelle ; sobriété, RGESN 1.6) : catalogue d'état, son brut ne garde que le dernier catalogue importé, et ceux pas encore importés (#139, journal ADR, 2026-10-19). Une base reconstruite n'en retrouve que l'état du dernier catalogue : ni les vulnérabilités retirées avant lui, ni les dates de révision passées, que seule la base garde. Un catalogue sans ligne n'est pas écrit (`empty_catalog`). Comme pour Zotero (fiche 2), `raw_data` peut garder le chemin d'un catalogue supprimé. |
| Sécurité | Données hors du dépôt de code (`KB_DATA_DIR`, `~/.knowledge_base`), jamais publiées ; fichiers lisibles par la seule utilisatrice ; l'API ouvre la base en lecture seule ; secrets en variables d'environnement. |

## Fiche 2 — Bibliothèque de lecture de l'utilisatrice

| Rubrique | Contenu |
|---|---|
| Finalité | Garder les papiers lus et les articles choisis par l'utilisatrice, avec ses surlignages, pour les rapprocher de la veille (bloc « Mes surlignages » des fiches). |
| Base légale | Intérêt légitime (art. 6.1.f) : l'utilisatrice traite ses propres données, pour son usage. |
| Personnes concernées | L'utilisatrice ; les auteurs des papiers gardés (déjà couverts par la fiche 1) ; les auteurs des articles gardés avec Web Clipper, et les personnes que leur texte nomme. |
| Données | Extrait JSON de la bibliothèque Zotero, écrit à chaque collecte : documents, auteurs, étiquettes, surlignages et commentaires, dates d'ajout, nom du fichier PDF ; pas les notes. Dans la base K-B (#138) : titre, type, URL et date d'ajout de chaque document ; texte, commentaire et date de chaque surlignage ; pas les auteurs, les étiquettes ni les PDF. Clips du Web Clipper (#14) : dans le brut, la copie telle quelle de chaque clip nouveau ou changé (frontmatter, dont `author`, et texte) ; dans la base K-B, la dernière version de chaque clip (#259) : titre, URL, date d'ajout, date de publication et texte gardé (`clip`), et la date de sa dernière révision (`revised_at`), et ses tags, normalisés (`tag`, `item_tag`, #260), pas `author`. Le coffre Obsidian lui-même reste chez l'utilisatrice : K-B le lit, n'y écrit rien. |
| Destinataires | L'utilisatrice ; les agents qu'elle lance, par l'API REST. |
| Transferts hors UE | Comme la fiche 1 : surlignages et texte des clips lus par un agent, envoyés au fournisseur du modèle. Les fiches de veille n'en reçoivent rien (section suivante). |
| Durée de conservation | Extraits Zotero du brut : **seul le dernier extrait importé est gardé**, avec ceux pas encore importés ; `kb import` supprime les autres une fois le nouveau importé (décision de Sabine du 2026-10-19, #139 ; procédure de tri, étape 7). Un extrait identique au dernier n'est pas écrit. Un extrait sans document, ou dont tous les documents sont invalides, n'est pas écrit : la collecte échoue. Limites : un extrait illisible n'est jamais importé, donc jamais supprimé par cette étape : il reste, sans durée, jusqu'à ce que l'utilisatrice le retire ; une bibliothèque vraiment vidée n'est plus collectée, la base garde son état précédent ; un extrait dont tous les documents passent la collecte mais sont refusés à l'import (par `Item` ou par la base) est importé quand même, et fait supprimer le précédent ; une base reconstruite depuis le brut n'a que l'état du dernier extrait : ni les documents et surlignages retirés avant lui, ni les dates de révision passées, que seule la base garde ; un document valide autrefois et refusé dans le dernier extrait reste en base, mais n'est plus dans le brut ; un item inchangé reste rattaché (`item.raw_data_id`) au fichier qui l'a écrit, et `raw_data` garde le chemin d'un fichier supprimé : le registre dit ce qui a été importé et quand, le fichier peut ne plus exister. Copies des clips du brut : gardées ; elles ne sont supprimées qu'une fois la base sauvegardée, au 08/11, avec PostgreSQL et Alembic (règle de Sabine du 2026-10-19 ; étape 8, pas encore codée). Clips dans la base : comme leur item ; un clip supprimé du coffre reste en base, seule la purge supprime. Tags dans la base (#260) : une liaison (`item_tag`) part avec son item (`ON DELETE CASCADE`) ; un tag que plus aucun item ne porte reste dans `tag`, gardé jusqu'à la purge (#83), pas avant le 08/11. Documents et surlignages dans la base : comme l'item auquel ils sont rattachés ; un document ou un surlignage supprimé dans Zotero est marqué retiré (`withdrawn_at`), pas supprimé (décision de Sabine du 2026-10-13) : seule la purge supprime. Zotero et le coffre Obsidian : gérés par l'utilisatrice dans ces outils, pas par K-B. |
| Sécurité | Comme la fiche 1. La base Zotero n'est lue que par une copie temporaire, supprimée à la fin de chaque extraction ; ni cette copie ni les extraits ne sont publiés ou versionnés. |

## Envoi des items au modèle des fiches (Azure AI Foundry)

Pour rédiger les fiches de veille (`docs/fiches-veille.md`), l'API IA envoie des champs des items
au modèle, chez Microsoft. C'est un traitement de la fiche 1 ; la fiche 2 n'envoie rien : ni
`zotero_entry` ni clip ne sont lus pour les fiches (`WatchKind`, `src/k_b/ai_api/watch_items.py`).
Sources datées : section « Sources de l'envoi au modèle ».

| Rubrique | Contenu |
|---|---|
| Données envoyées | La liste blanche de #204 (`docs/fiches-veille.md`, « Entrée du modèle » ; `FIELDS_BY_KIND`, `src/k_b/ai_api/watch_items.py`) : `paper` : `title`, `summary` ; `vulnerability` : `cve_id`, `title`, `description`, `vendor`, `product`, `ransomware_use` ; `release` : `repository_name`, `tag_name`, `title`, `body` ; `advisory` : `ghsa_id`, `cve_id`, `title`, `cve_listed_in_cisa_kev`, `packages` ; `newsletter_article` : `edition`, `title`, `summary` ; plus `item_id` et `kind` pour chacun. Jamais `authors` (jamais lu par l'API IA) ni `url`. Dans chaque champ, toute URL devient `[url]` ; dans `release.body`, chaque `@login` devient `@user` ; puis chaque texte est coupé. Au classement, chaque item n'envoie que `item_id`, `kind`, `title` et son texte long (`summary`, `description` ou `body`) coupé à 500 caractères ; à la rédaction, les champs ci-dessus, coupés à 2 000 caractères (`MAX_FIELD_CHARS_FOR_WRITING`, `src/k_b/core/config.py`). |
| Données personnelles qui partent | Le login du propriétaire d'un dépôt, dans `repository_name` (`owner/repo`), quand c'est une personne : gardé, car il identifie le dépôt. Limites du masquage (`docs/fiches-veille.md`) : une adresse mail écrite dans `release.body` et un nom écrit en texte libre (notes d'une release, résumé d'un papier ou d'un article) partent tels quels. |
| Destinataire | Microsoft, par Azure AI Foundry : le déploiement `gpt-6-luna` (version 2026-09-22, journal ADR, « Modèle des fiches : gpt-6-luna sur l'abonnement de l'organisme de formation », 17/10), pour le rédacteur (`KB_LLM_MODEL`) comme pour le LLM juge (`KB_LLM_JUDGE_MODEL`) : le juge suit le repli du déploiement décidé le 16/10 (`docs/fiches-veille.md`, « Juge », « Réglage » ; décision de Sabine du 17/10 pour les phases 1 et 2 du projet ; le juge définitif se choisit en phase 3, et le registre sera mis à jour avant tout envoi de données réelles à un autre déploiement). Le juge reçoit les affirmations gardées et les mêmes champs, coupés et masqués, des items qu'elles citent : les mêmes données partent une seconde fois, vers le même déploiement. Microsoft n'en donne l'accès ni à OpenAI ni aux autres fournisseurs de modèles (« are NOT available to OpenAI or other providers of Models sold by Azure »). |
| Fondement de la sous-traitance | Le contrat de formation de l'utilisatrice : son organisme de formation lui fournit, dans son propre abonnement Azure, une ressource pour y déployer le projet de certification, dont K-B fait partie (décision de Sabine du 2026-10-17, lecture retenue parmi trois). Le client de Microsoft est l'organisme : l'abonnement (« Plan Azure », c'est-à-dire l'offre du Microsoft Customer Agreement), son annuaire et le compte de connexion de l'utilisatrice sont les siens ; elle n'a sur l'abonnement que le rôle « Lecteur » et n'a accès à aucun compte de facturation (constats de Sabine dans le portail Azure, 2026-10-17) ; son rôle sur la ressource ou son groupe est supérieur à « Lecteur » (elle a déployé le modèle et lu la clé), non relevé. Le DPA de Microsoft, qui « governs data processing by Models sold by Azure » (page « Data, privacy, and security »), fixe les rôles entre Microsoft et son client : « Customer is the controller of Personal Data and Microsoft is the processor of such data, except (a) when Customer acts as a processor of Personal Data, in which case Microsoft is a subprocessor » (DPA du 22/05/2026, « Processor and Controller Roles and Responsibilities »). Le Microsoft Customer Agreement incorpore les Product Terms et le DPA ; les Privacy and Security Terms du programme Microsoft Customer Agreement rangent « Foundry Models sold by Azure » dans les Azure Core Services. Contrat de formation non relu ; aucune clause de l'art. 28 identifiée. Options écartées par Sabine : écrire une limite assumée, la chaîne utilisatrice → organisme → Microsoft n'étant pas contractualisée (comme pour Gemini le 16/10) ; ne pas envoyer de données réelles sur cet abonnement (la mesure de #158 se fait sur une veille réelle). Le compte personnel en Microsoft Customer Agreement, lu le 2026-10-16, n'est plus utilisé : son quota de `gpt-6-luna` était à 0. Un changement d'abonnement ou de compte de facturation (par exemple l'abonnement d'une autre école, ou celui de la mise en ligne du 08/11) oblige à relire le type du compte et la chaîne contractuelle avant le premier appel sur ce compte. |
| Destinataires possibles chez l'organisme | L'abonnement et son annuaire étant ceux de l'organisme : un administrateur général de l'annuaire peut se donner l'accès à tous les abonnements de l'annuaire, donc à la ressource et à ses clés (« elevate access ») ; si l'organisme active la protection des services d'IA de Microsoft Defender for Cloud avec les preuves des prompts (« user prompt evidence »), des extraits des prompts et des réponses apparaissent dans ses alertes de sécurité, données sensibles masquées automatiquement (rôle Owner ou Contributor requis pour l'activer) ; les politiques Azure de l'organisme sur les journaux de diagnostic ne sont pas connues. Tout propriétaire (Owner) ou contributeur (Contributor) de l'abonnement ou du groupe de ressources peut lire les clés, et modifier ou recréer le déploiement (zone, version) sans que K-B le détecte ; si le plan IA de Defender est actif, les prompts et les réponses sont stockés 30 jours chez Microsoft, en un lieu qui dépend de l'annuaire de l'organisme. Aucune de ces fonctions n'est activée par K-B. |
| Région | Ressource en France Central, déploiement de type Zone de données standard (le portail affiche « Votre déploiement dans francecentral traitera les données dans la zone de données EUR ») ; version figée (2026-09-22, « Refuser les mises à niveau automatiques »). Un premier déploiement en Global Standard (traitement possible dans toute région Azure) a été écarté le 2026-10-17. Pour un déploiement Data Zone dans une ressource située dans l'UE : « prompts and responses may be processed in that or any other European Union Member Nation » ; les données au repos, dont celles de la surveillance des abus, sont stockées dans la géographie de la ressource. |
| Usage par le fournisseur | Ni entraînement ni amélioration des modèles : « prompts and completions are not used to train, retrain, or improve the base models » ; « The models are stateless: no prompts or completions are stored in the model » : c'est le modèle qui ne garde rien, pas le service (la surveillance des abus, ci-dessous, et les fonctions avec état en gardent). Surveillance des abus : la revue automatique ne stocke rien ; seules les demandes signalées par le système, ou qui font partie d'un usage qu'il juge potentiellement abusif, sont stockées pour une revue humaine, par des employés de Microsoft situés dans l'EEE pour un déploiement dans l'EEE. K-B n'appelle que `chat/completions`, sans `store` (`src/k_b/ai_api/connectors/llm_client.py`) : aucune des fonctions qui gardent des échanges chez Microsoft (Responses API, Assistants, Stored completions). **Cache de prompt coupé** : à partir de GPT-5.6, le service écrit par défaut un cache sur le dernier message de chaque requête (donc sur le texte des items), réutilisable « for at least 30 minutes, but the service might retain it longer », jamais partagé entre abonnements ; K-B envoie à chaque requête `prompt_cache_options: {"mode": "explicit"}` sans point d'arrêt, qui n'écrit aucun cache (`build_request_body`, `src/k_b/ai_api/connectors/llm_client.py` ; décision du 2026-10-17, tranchée par time-knight sur délégation de Sabine : une correction de minimisation). Vérifié une fois, à l'essai de #158 (2026-10-17) : `usage.prompt_tokens_details.cache_write_tokens` vaut 0 sur 20 réponses (`cached_tokens`, à 0 aussi, compte les lectures du cache, pas les écritures) ; le client ne suit pas ce champ en production. Option écartée : garder le cache et le décrire ici (une rétention de plus, pour un gain presque nul : chaque message de K-B est différent). |
| Durée de conservation | Chez K-B : rien, l'API IA n'écrit rien (règle 7 de `.claude/rules/poc.md`). Chez Microsoft : revue automatique, aucun stockage ; données gardées pour la revue humaine, **durée non publiée** par Microsoft (ni la page « Data, privacy, and security » ni la page « Abuse monitoring » ne la donnent). Une durée de 30 jours n'apparaît que dans des réponses de Microsoft Q&A et des sources secondaires : elle n'est pas retenue ici. |

## Procédure de tri

Chaque étape dit ce qu'elle fait, si elle est automatisée, et sa fréquence. Le code de la purge
relève de #20 ; chaque passage journalise ce qu'il a supprimé (nombre de lignes et de fichiers,
jamais les noms).

| # | Traitement | Étape | Automatisée | Fréquence |
|---|---|---|---|---|
| 1 | Veille (fiche 1) | Les logins GitHub des champs d'auteur et de crédit (auteurs, personnes créditées) ne sont pas lus dans les items ; GH Archive ne sélectionne pas `actor`. Les notes d'une release sont lues telles que reçues, avec les logins ou @mentions qu'elles contiennent. | oui, à la lecture et à la requête | à chaque collecte (une par jour) |
| 2 | Veille (fiche 1) | Supprimer les items collectés depuis plus longtemps que la durée de leur mode d'acquisition (`src/k_b/core/config.py` ; 2 ans pour la veille). Les auteurs d'un papier partent avec lui : ils sont une colonne de `publication`. Constat : le schéma n'a de suppression en cascade ni vers les sous-types (`release`, `advisory`, `newsletter_article`, `zotero_entry`, `clip`) ni vers les référentiels (`publication`, `vulnerability`). Les liaisons d'un item purgé à ses tags (`item_tag`) partent avec lui, en cascade (#260) ; la purge supprime ensuite les tags sans liaison (`tag`). Les lignes de `trend` ne sont pas des items : leur purge n'est pas définie (journal ADR, « Décisions encore ouvertes »). | prévue en dernière étape de la collecte ; pas encore codée (#83) | à chaque collecte (une par jour) |
| 3 | Veille (fiche 1) | Supprimer les fichiers bruts de `raw/automated_watch/` plus anciens que la durée du mode `watch` (`src/k_b/core/config.py` ; 2 ans). | prévue après l'étape 2 ; pas encore codée (#83) | à chaque collecte (une par jour) |
| 4 | Bibliothèque (fiche 2) | Supprimer la copie temporaire de la base Zotero : après un succès, une erreur ou un Ctrl-C ; une copie laissée par un processus tué est retirée au début de l'extraction suivante. | oui, à chaque extraction (testé) | à chaque collecte |
| 5 | Les deux | Demande d'une personne. Accès : lui dire ce qui est gardé à son nom. Effacement ou opposition : supprimer son nom de la base, supprimer les fichiers bruts qui le contiennent, et noter le nom dans une liste d'exclusion lue par l'import, pour qu'une collecte ou une reconstruction ne le réintroduise pas. Dans la base, un nom d'auteur est dans la liste JSON de chaque papier (`publication.authors`) et un login peut être dans les notes d'une release (`release.body`) : l'effacement réécrit ces valeurs, ce n'est pas une suppression de ligne. Le login d'un propriétaire est aussi dans le nom d'un dépôt d'un classement (`trend.repository_name`) : là, l'effacement supprime la ligne. Un nom peut être dans le titre ou le texte d'un clip (`clip.title`, `clip.body`) : l'effacement réécrit ces valeurs, et la copie brute du clip. Limite (#259) : un clip du coffre recopié (une édition, une étiquette du Finder, un `chmod` suffit) diffère de la base effacée et la réécrit, nom compris ; l'effacement touche donc aussi le clip du coffre, ce que fait l'utilisatrice, K-B n'y écrivant jamais. Un nom peut aussi être un tag (`tag.name`, #260), partagé par plusieurs clips : la recherche par nom lit aussi `tag.name` et ses liaisons (`item_tag`), et trouve ainsi les tags que plus aucun clip ne porte ; l'effacement réécrit ou supprime le tag, pour tous les clips qui le portent, et le tag dans chaque clip du coffre. | non | à la demande, sous un mois (art. 12.3) |
| 6 | Les deux | Relire ce registre : sources ajoutées, champs ajoutés à la base, durées. | non | une fois par an, et à chaque nouvelle source |
| 7 | Bibliothèque (fiche 2) et veille (fiche 1) | Catalogues d'état, extraits Zotero et catalogues CISA KEV : une fois un nouveau fichier importé, supprimer du brut ceux importés avant lui. La liste vient du registre de la base (`raw_data`), jamais du dossier : un fichier pas encore importé, ou illisible, n'est jamais supprimé ; rien n'est supprimé si le dernier fichier importé manque. Journal : un nombre de fichiers, jamais un nom (`src/k_b/etl/raw_purge.py`). Limite : seuls les deux dossiers `raw/selected_library/zotero/` et `raw/automated_watch/cisa_kev/` sont purgés ; un dossier renommé à la main (`cisa_kev_<suffixe>`) ne l'est pas. | oui, à la fin de `kb import`, après le commit (testé) | à chaque import |
| 8 | Bibliothèque (fiche 2) | Supprimer les copies des clips du brut (`raw/selected_library/clipping/`, copies et recopies), une fois la base sauvegardée : une sauvegarde native de PostgreSQL se migre par `alembic_version`, un export CSV non. K-B ne touche jamais au coffre Obsidian. | prévue au 08/11 ; pas encore codée | à définir avec la sauvegarde |
| 9 | Les deux | Le *curated* (fiches de lecture, fiches de veille, wiki, classements et tendances) n'est jamais purgé automatiquement ; le *cleansed* (la base, et les `.md` normalisés) est immuable (journal ADR, 2026-10-19), au sens précisé par Sabine le même jour : un `.md` importé dont le contenu change est réécrit en base, `revised_at` daté (journal ADR, 2026-10-19, « Collecte : mise à jour des `.md` importés », #259). | sans objet | — |

L'étape 5 est une exception assumée à la règle du brut jamais modifié : une obligation légale
prime. La liste d'exclusion est elle-même une donnée personnelle ; elle vit hors du dépôt, avec
les données.
